Nginx 설정을 읽을 때는 지시어의 이름과 함께 어느 블록에 들어 있는지 확인한다. 같은 파일 안에서도 전체 프로세스 설정, HTTP 공통 설정, 도메인별 설정, URL 경로별 설정의 범위가 다르다. 이 글에서는 기본 설정 파일부터 HTTPS와 리버스 프록시까지 연결해 본다.

## main·http·server·location의 범위

최상위에는 워커 프로세스 같은 공통 설정을 둔다. `events`는 연결 처리 설정을 담고, `http` 안에는 HTTP 공통 설정과 `server` 블록을 둔다. `server`가 도메인과 포트를 선택하고, 그 안의 `location`이 URL 경로별 처리를 나눈다.

```code
# Main context
user www-data;
worker_processes auto;
pid /run/nginx.pid;
events {
    worker_connections 1024;
}

# HTTP context
http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    sendfile on;
    keepalive_timeout 65;

    # Gzip 설정
    gzip on;

    # Server block
    server {
        listen 80;  # HTTP 포트
        server_name example.com www.example.com;

        # 로그 파일 경로
        access_log /var/log/nginx/example.access.log;
        error_log /var/log/nginx/example.error.log;

        # Location block
        location / {
            root /var/www/html;
            index index.html index.htm;
        }

        # 특정 경로에 대한 설정
        location /images/ {
            alias /var/www/images/;
        }

        # 리버스 프록시 설정
        location /api/ {
            proxy_pass http://localhost:3000;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}

```

위 예제에서 `/`는 정적 파일을 제공하고 `/images/`는 별도 디렉터리를 가리킨다. `/api/` 요청은 3000번 포트의 애플리케이션으로 전달한다. 프록시 설정을 바꿀 때는 전달되는 URI와 Host 헤더, 원래 요청의 주소·프로토콜 정보가 의도대로 도착하는지 확인한다.

## HTTPS 인증서 연결

HTTPS용 `server` 블록에는 인증서와 개인 키 경로를 지정한다. 아래 경로와 도메인은 예시이므로 발급받은 인증서와 서버 환경에 맞춰 바꾼다.

```code
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /etc/nginx/ssl/example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    location / {
        root /var/www/html;
        index index.html;
    }
}
```

설정을 반영한 뒤에는 인증서의 도메인과 유효 기간, 인증서 체인을 확인한다. 파일 경로가 틀리거나 개인 키를 읽지 못하면 설정 검사 단계에서 실패할 수 있다.

## HTTP 요청을 HTTPS로 이동

80번 포트로 들어온 요청을 HTTPS 주소로 이동시키려면 다음과 같이 `return`을 설정한다. 앞의 HTTP 서비스 예제 대신 사용하는 블록이다.

```code
server {
    listen 80;
    server_name example.com www.example.com;
    return 301 https://$host$request_uri;
}
```

`curl -I http://example.com`으로 응답 코드와 `Location` 헤더를 확인한다. `www.example.com`도 받을 경우 HTTPS 설정과 인증서가 그 호스트까지 처리하는지 점검한다.

## 수정 후에는 반드시 검증

설정을 바꾼 뒤에는 먼저 문법과 참조 파일을 검사한다. 검사가 성공한 경우에만 reload한다. 아래 명령은 systemd에서 `nginx` 서비스로 실행하는 환경을 기준으로 한다.

```bash
# 설정 검사에 성공했을 때만 다시 불러오기
sudo nginx -t && sudo systemctl reload nginx
```

설정 검사가 통과해도 애플리케이션 응답까지 보장되지는 않는다. reload 후에는 실제 URL로 요청을 보내고 access/error 로그를 확인한다. reload의 처리 방식과 설정 블록 설명은 [Nginx 공식 입문 문서](https://nginx.org/en/docs/beginners_guide.html)를 참고한다.
