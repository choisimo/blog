## 결론

기존 소스에 메모장 작업 공간, 사용자별 응답 설정, Chat/토론의 이미지 카드, 서버 이미지 한도와 비공개 저장 경로를 구현했다. 실제 배포와 유료 provider 호출은 하지 않았다. 새 이미지 기능은 연결·권한·저장소를 검증한 뒤 활성화하도록 기본값을 꺼 두었다.

일반 회원가입은 이번 변경에서 새로 구현하지 않았다. 현재 인증은 익명 JWT와 관리자 인증 중심이다. 아래의 일반 회원가입·이관·남용 대응 계획을 관리자 인증 완화로 대신해서는 안 된다.

## 1. 메모장에서 바뀌는 점

기존 메모장은 여러 도구와 작성/미리보기 영역이 동시에 공간을 차지했다. 본문을 먼저 쓰고 필요한 도구만 여는 구조로 바꿨다.

| 항목 | 변경 내용 | 계속 유지하는 것 |
|---|---|---|
| 기본 작업 공간 | 단일 작성 영역이 기본. 큰 화면에서 분할 미리보기 선택 | 기존 Markdown 작성/미리보기 기능 |
| 문서 탐색 | 제목에서 자동 목차 생성, 제목을 눌러 해당 위치로 이동 | 코드 블록 안의 `#`는 목차로 잘못 수집하지 않음 |
| 검색 | Ctrl/Cmd+F 문서 내 검색, 이전/다음, Enter/Shift+Enter, Esc | 검색 Esc가 메모장 자체를 닫지 않음 |
| 집중 모드 | 제목·본문 중심으로 도구/탭/부가 영역 축소, Esc로 복원 | 문서와 선택한 내용을 그대로 유지 |
| 제목·도구 | 제목을 눌러 바로 수정. 코드 도구는 한 줄로 접어 필요할 때 펼침 | 언어 선택·복사·실행, 기존 기능 접근 경로 |
| 모바일 | 좁은 화면의 목차 drawer, 한 줄 하단 작업, 화면 높이 활용 | 기존 메모/버전/제안·관리 기능 |
| 저장 | 저장 성공을 확인한 후 표시. 실패 시 실패 안내, 저장 후 닫기 중단 | `aiMemo.content` 등 기존 저장 key와 자료 |
| 동작 효과 | 패널 열기, 목차/검색 펼치기, 버튼 상태/선택 전환 | reduced-motion에서는 새 애니메이션 비활성화 |

읽기 공간을 확보하기 위해 평소 줄 번호와 반복 표시를 숨기되, 코드 실행·기록·다운로드·클라우드 동기화 자체를 삭제하지 않았다. 기존 사용자의 글꼴 크기는 유지하고 새 사용자의 기본 크기를 16으로 조정했다. 라이트/다크/터미널 테마를 지원한다.

관련 파일: `frontend/public/ai-memo/ai-memo.js`, `memo-workspace.css`, `frontend/index.html`. HTML script query와 내부 stylesheet query를 함께 갱신했다.

## 2. Chat와 AI 토론에 이미지가 붙는 방식

글과 이미지 생성은 서로 기다리지 않는다. Chat는 수신한 텍스트를 약 80ms 간격으로 화면에 반영하며, 응답 본문이 준비되면 별도 이미지 카드가 동작한다. 토론방에서는 실제 토론 텍스트가 들어온 뒤 주제 이미지를 요청한다. Chat 내부 찬반 토론은 첫 응답에 주제 카드 하나를 붙이며 라운드마다 자동으로 새 이미지를 만들지 않는다.

이미지 설정은 네 가지다.

| 설정 | 동작 |
|---|---|
| 관련 주제에 자동 | 이미지·구조·비교·설계 등 키워드가 있는 Chat 질문에 생성. 토론은 주제 카드 생성 |
| 답변마다 | 본문이 준비된 답변마다 생성 요청. 한도는 그대로 적용 |
| 직접 눌러 생성 | 사용자가 이미지 버튼을 눌렀을 때만 생성 |
| 사용 안 함 | 새 이미지 생성 버튼과 자동 요청을 끔. 이미 받은 이미지는 유지 |

현재 자동 판단은 키워드 기반 규칙이며, 별도 AI 판단으로 주제를 분류하는 기능은 아니다. 이미지의 주제 입력은 질문/토론 맥락을 사용한다. 여러 장을 동시에 생성하거나 모델이 임의 URL을 제시하는 방식은 아니다.

이미지를 크게 보기, PNG 저장, 생성 상태 확인, 실패 안내를 구현했다. 저장된 주소는 소유자를 확인하는 전용 endpoint로만 읽는다. 그림은 “AI 생성 · 참고 이미지”로 표시한다. 토론에서는 한쪽 주장의 증거인 것처럼 보이지 않는 주제 삽화를 요청하며, 실제 수치 차트·문헌·증거 사진을 대신하지 않는다.

이미지가 실패해도 텍스트를 지우지 않는다. Chat 스트림이 중간에 끊겨도 이미 받은 텍스트를 보존한다. 이미지 연결이 끊어졌다는 이유로 같은 유료 요청을 자동 재전송하지 않는다.

## 3. 사용자가 관리하는 AI 설정

Chat·토론·메모장에서 같은 설정 화면을 연다. 역할, 직접 작성한 역할 설명, 말투, 길이, 언어, 표 사용, 근거/불확실성 표시, 이미지 생성 방식, 그림 표현, 비율을 관리한다.

기존의 특정 캐릭터 말투 강제와 토론의 고정 2~4문장 지침을 제거했다. 대화용 설정이 실제 요청에 전달되며 서버에서 허용된 값만 다시 정리한다. 일반 Chat, 토론 Chat, 세션 통합 답변에 반영한다. 내부 도구의 JSON 출력 계약이나 관리자 도구 권한을 바꾸는 설정은 아니다.

| 비회원 | 검증된 로그인 계정 |
|---|---|
| 해당 브라우저의 로컬 설정 사용 | 계정별 로컬 캐시와 D1 설정 저장 |
| 다른 기기로 자동 동기화하지 않음 | 새 기기에서 계정 설정을 읽을 수 있음 |
| 브라우저 데이터 삭제 시 설정 소실 가능 | 서버 저장에 성공한 설정은 계정에 남음 |

계정 설정에는 버전 번호를 둬 오래된 화면의 저장이 다른 기기의 수정을 덮어쓰지 않게 했다. 충돌하면 다시 불러오도록 안내한다. 계정이 바뀌는 도중의 저장과 과거 대화에 의한 새 계정 이미지 요청을 막았다.

서버 설정을 읽지 못한 경우 화면에 로컬 저장 상태를 표시한다. 로컬 전용 변경을 자동 병합하는 오프라인 동기화 엔진은 구현하지 않았다. 다음 동기화에서 어떤 값을 채택할지 명시적으로 선택하는 개선이 필요하다.

`role=researcher` 같은 대화 역할과 JWT의 `role=user/admin` 같은 계정 권한은 별개다. 클라이언트는 관리자 권한, 이미지 한도, provider 모델, API 키, 도구 실행 권한을 직접 바꿀 수 없다.

## 4. 비회원 하루 5장 제한

### 무엇으로 구분하는가

익명 방문자도 JWT를 받기 때문에 토큰의 존재만으로 회원을 판정하지 않는다. 서버가 서명·유효성을 확인한 JWT에서 `sub`가 있고, `role`이 `user/member/admin`, `emailVerified=true`, refresh token이 아닌 경우에만 회원 한도를 사용한다. 나머지는 비회원 정책을 적용한다.

클라이언트 body의 `userId`, `tier`, `role`, `n`, `model`은 이미지 요청 필드로 허용하지 않는다. 요청당 이미지 수는 서버가 1장으로 고정한다.

### 적용 정책

| 구분 | 비회원 | 회원 |
|---|---|---|
| 하루 이미지 | **5장 고정** | **20장 기본 제안값**, 환경 설정으로 조정 |
| 한도 기준 | 익명 주체 + 같은 날의 신뢰된 네트워크 식별자 | 계정 ID |
| 갱신 | 한국 시간 00:00 | 동일 |
| 여러 탭/기기 | 동일 네트워크 비회원 한도도 검사 | 같은 계정이면 한도 공유 |
| 설정 저장 | 이 기기 | 계정 저장 + 로컬 캐시 |
| 이미지 접근 | 생성한 익명 주체만 | 생성한 계정만 |
| 이미지 보관 | 현재 7일 | 현재 7일 |
| 모델·품질 | 운영 서버에서 결정 | 운영 서버에서 결정 |

회원 20장은 사용자가 확정한 사업 정책이 아니라 초기 운영 제안값이다. 일반 회원에게 무제한을 제공하지 않는다. 별도로 전체 서비스 하루 500장 기본 상한과 분당 5회 요청 제한을 둔다. 실패 요청도 짧은 시간 요청 제한에 포함해 무한 실패 재시도로 provider를 두드리지 않게 한다.

### 동시에 요청되거나 결과가 불분명할 때

D1의 한 SQL 문장에서 사용량 조건 확인과 예약 행 삽입을 함께 수행한다. “잔여량 조회 후 별도로 차감”하는 두 요청으로 구현하지 않았다. 같은 요청 key는 중복 예약하지 않는다.

```text
이미지 요청
  → 서버가 사용자·요청 형식·서비스 설정을 확인
  → 한도 안에서 1장 자리 확보
  → Backend → AI-server에 n=1 요청
  → 이미지 검증·비공개 저장 완료 → 결과 공개

명확한 생성 거절 → 해당 자리 반환
연결 끊김·결과 불명 → 자리는 유지, 같은 작업 상태만 확인
한도 도달·저장소 미설정 → provider 호출하지 않음
```

명확한 거절과 결과를 알 수 없는 실패를 구별했다. 후자는 이미지가 이미 생성돼 비용이 발생했을 수 있으므로 자동으로 차감 취소하거나 재생성하지 않는다. 결과 복구·운영 정산 UI는 추가 작업으로 남아 있다.

### 비회원 식별의 한계

이 구현은 비회원 **실제 사람 한 명**을 완벽히 식별하는 시스템이 아니다. 브라우저 데이터 삭제에 의한 쉬운 초기화를 줄이기 위해 Cloudflare가 주입한 IP를 일별 HMAC 식별자로 바꿔 보조 한도로 사용한다. raw IP를 새 이미지 작업 테이블에 저장하지 않는다. `X-Forwarded-For`를 신뢰하지 않는다.

같은 회사·학교·가정의 여러 비회원은 5장 한도를 공유할 수 있다. 반대로 IP/네트워크가 바뀌는 사용자나 분산 봇까지 완벽히 묶지는 못한다. IPv6 subnet 정규화, Turnstile, 악용 탐지, 회원 전환 제한은 후속 정책이다. 이러한 한계를 숨기고 “우회 불가능한 개인별 제한”이라고 안내하면 안 된다.

## 5. 회원가입과 비회원 전환 계획

### 현재 경계

현재 OAuth는 `ADMIN_ALLOWED_EMAILS` 중심 관리자 인증이다. 이것을 완화해 일반 회원가입처럼 사용하는 방식은 금지한다. 일반 회원 인증 경로와 관리자 인증 경로, return URL 허용 범위, token 발급 정책을 분리한다.

### 가입 후 달라지는 것

이메일 인증 또는 검증된 OAuth identity를 거친 안정적인 계정 ID를 발급하고 일반 계정의 역할을 서버에서 `user`로 고정한다. 비인증 상태는 계속 비회원 한도를 적용한다. 여러 기기 로그인은 한 계정 한도를 공유하고 관리자 기능은 열어주지 않는다.

기기 메모·설정·대화를 가입 즉시 몰래 가져오지 않는다. 가입 직후 “이 기기의 내용을 계정에 가져오기”를 선택하게 하고 실제 소유를 확인할 수 있는 항목만 이관한다. 로컬 단독 메모의 랜덤 ID를 검증된 소유권으로 간주하지 않는다.

동일 날짜 비회원 5장을 사용한 뒤 회원이 된 경우, 현재 구현은 guest/member가 별도 주체이므로 회원 예산이 새로 적용된다. 정식 가입 도입 시에는 검증된 전환에 대해 사용량을 합산하고, 같은 비회원 사용량을 여러 계정으로 반복 이전하지 못하도록 전환 ledger를 두는 것을 권한다. 이는 아직 구현되지 않았다.

### 가입 유도 방식

글 읽기·기본 대화·메모장은 가입 배너로 가리지 않는다. 이미지 한도에 도달했을 때 남은 시간과 계정 기능 차이를 짧게 알린다. 실제 일반 회원가입 경로가 배포된 뒤에만 가입 버튼을 활성화한다. 관리자 로그인 페이지를 일반 가입 대안으로 제시하지 않는다.

등록 회원의 핵심 차이는 더 큰 명시적 예산, 설정 동기화, 계정 단위 생성물 관리다. 고품질 모델을 제공한다고 임의로 약속하거나 비회원 답변을 의도적으로 나쁘게 만들 필요는 없다.

### 데이터 관리

계정 비활성화·탈퇴 시 token을 철회하고 설정 및 생성물 삭제 흐름을 둔다. 긴 보관 기간은 회원의 선택과 운영 비용 검토 후 별도 정책으로 도입한다. 공개 공유/SEO 사용은 기본 비공개 이미지에서 별도 동의·복제·공개 절차를 거친다.

| R06 일반 회원가입·이관 | 계획 | 관리자 인증 분리, 이메일 검증, guest 이관 ledger |
| R07 악용 대응·결과 복구 | 계획 | Turnstile·분산 요청 대응, provider 결과 조회, 운영 정산 |

## 7. 검증 결과를 해석하는 범위

실제 정책 함수와 실제 migration/SQL을 사용한 Node 테스트 26개가 통과했다. 여기에는 독립 SQLite 연결 8개를 병렬로 실행해 예약이 정확히 5개까지만 들어가는 테스트, 공유 네트워크 제한, 회원/전역 상한, 확실한 실패와 불명확한 결과의 차이, 보관 기간 회수, 설정 버전 충돌, public route 소유권이 포함된다.

실제 메모장 JS/CSS를 Chromium에 로드해 라이트/다크/터미널 × 320/390/1360px 조합을 확인했다. Storage-compatible 메모리 어댑터와 오류 주입을 사용했으며, 실제 persistent storage나 실제 로그인 서버를 사용한 E2E는 아니다.

TypeScript transpile 진단, JS syntax, CSS parse는 통과했다. 이것은 전체 TypeScript 타입 검사나 frontend 번들 성공을 뜻하지 않는다. npm dependency 설치가 완료되지 않았고 offline cache에는 `zwitch`가 없어 전체 build/Vitest/Hono integration을 실행하지 못했다. 실제 AI-server 이미지 호출과 운영 배포 역시 미실행이다.

검증 스크립트·로그·실제 컴포넌트 스크린샷은 `scripts/verification/`과 `verification/reader-experience/`에 있다. 배포 명령과 설정 순서는 같은 폴더의 `DEPLOYMENT.md`를 따른다.
