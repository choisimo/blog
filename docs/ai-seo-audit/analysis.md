# 블로그 AI·이미지·콘텐츠·SEO 개선 분석

**기준:** 2026-09-10 KST · 첨부 source-repro snapshot `3ece77621379` / dirty

## 결론

현재 가장 큰 문제는 기능의 부족보다 **요청 접수, 실제 실행, 검증된 결과 공개가 서로 다른 경로로 나뉘어 있다는 점**이다. 번역은 대기열에 들어간 뒤 화면만 먼저 실패하고, Projects는 데이터 조회 실패가 빈 목록 성공으로 바뀌며, SEO 게이트웨이는 검색봇의 자산 요청까지 HTML로 바꾼다. 이미지 생성은 관리자 화면·백엔드 어댑터·저장·에이전트 도구가 이미 있으므로 새로 만드는 대신 기존 기능을 완결해야 한다.

우선순위는 번역 실행 경로와 SEO 응답 오류 복구, Projects 데이터 전달 복구, 사용자 대기·취소 경험 개선, 이미지 작업의 내구성 확보, 검증된 콘텐츠만 공개하는 SEO 자동화 순이다. 검색 순위 상승은 보장할 수 없지만, 크롤링 방해와 잘못된 메타데이터부터 제거하고 개선 결과를 측정하는 시스템은 설계할 수 있다.

### 실제 콘텐츠 집계

`posts-manifest.json`의 전체 항목은 282개, `published !== false`인 공개 항목은 140개다. 이 중 대표 이미지 필드가 있는 항목은 52개, 지정되지 않은 항목은 88개다. 설명 미지정 1개, 태그 미지정 7개, 언어 필드 미지정 140개가 확인됐다. 언어는 원문 frontmatter에서 따로 얻을 수 있으므로 140개가 잘못된 언어라는 뜻은 아니다.

대표 이미지가 없는 글에도 기존 동적 OG 이미지 fallback이 있으므로 “88개에 공유 이미지가 전혀 없다”는 뜻이 아니다. 이미지 없는 본문이 의도된 글도 있을 수 있다. `sitemap.xml`에는 URL 144개, RSS에는 항목 20개가 기록돼 있다. 숫자의 존재와 검색봇에게 정상 제공되는지는 별도 검증 대상이다.

## 1. AI 번역이 동작하지 않는 이유

### 1.1 가장 먼저 고칠 부분: 화면은 20초를 기다리지만 실제 작업은 별도로 대기한다

현재 공개 화면은 원문과 번역 캐시를 조회한다. 유효한 번역이 없으면 서버는 `translation.generate` 작업을 outbox에 기록하고 `202`와 `Retry-After: 15`를 돌려준다. 이 공개 요청 자체가 작업을 즉시 소비하지 않는다. 브라우저는 15초 간격 안내를 따르지만 전체 관찰 시간은 20초뿐이다. 따라서 작업이 정상 대기 중이어도 먼저 `AI_TIMEOUT`으로 바뀐다. [E01]

포함된 설정에서 outbox를 주기적으로 소비하는 cron은 `0 6 * * *`, 즉 매일 06:00 UTC / 15:00 KST다. 관리자·internal flush 경로도 있으나 저장소 안에서는 별도의 반복 호출을 확인하지 못했다. **외부 실행기가 추가로 연결돼 있지 않다면** 사용자가 방금 요청한 번역이 하루 한 번 처리되는 경로를 기다리게 된다. 운영 서버에서 실제로도 그런지는 배포 설정과 호출 기록으로 확인해야 한다. [E02]

```text
현재: 언어 변경 → 캐시 없음 → outbox 등록 → 202
                                  ├─ 화면: 최대 20초 뒤 오류
                                  └─ 작업: 별도 소비자가 나중에 실행

개선: 언어 변경 → 캐시 조회 → 동일 버전 작업 확인/접수 → 즉시 소비 신호
                                  ├─ 원문을 계속 읽을 수 있음
                                  └─ 준비됨을 확인한 뒤 번역 표시
```

단순히 브라우저 제한을 20초에서 2분으로 늘리는 것으로는 실행되지 않은 작업을 고칠 수 없다. 작업 실행 보장과 사용자 화면의 관찰 시간을 분리해야 한다.

### 1.2 사용자 요청에도 백그라운드 준비 작업의 중단 조건이 적용된다

outbox 소비는 Redis 정상, queue enabled, asyncMode enabled를 모두 요구하며 공급자 중 하나라도 down이면 전체를 중단한다. 백엔드의 기본 `AI_ASYNC_MODE`는 false다. 해당 기본값을 그대로 사용하면 동기 AI API가 동작하더라도 outbox는 `queue-unavailable`로 멈출 수 있다. payload에는 interactive 우선순위를 넣지만 실제 claim은 생성일 순이다. [E03]

일반 번역은 기존 D1 outbox를 재사용하되 사용자 요청과 선택적 선생성의 처리 조건을 분리하는 편이 좋다. 사용할 공급자 경로가 가능한지 검사하고, 다른 공급자의 실패로 모든 번역을 막지 않아야 한다. 우선순위는 payload 표시가 아니라 실제 소비 순서에 반영한다. 소비자의 임대 만료·재시도·재실행도 동일 작업 기록에서 관리한다.

### 1.3 일부 글은 요청 자체가 차단된다

프론트엔드 slug 정규식은 영문/숫자로 시작하는 제한된 문자열만 허용한다. 실제 공개 manifest를 대조하니 다음 3개가 거부됐다. [E04, 진단 T01]

| 연도 | slug |
|---|---|
| 2026 | `Container Network Interface` |
| 2025 | `감동을_잃어버린_그대들에게` |
| 2024 | `_index` |

서버 요청 전에 실패하므로 이 경우 모델이나 API 키를 바꿔도 해결되지 않는다. 공개 글 ID/manifest에 존재하는 항목을 기준으로 식별하고, Unicode 정규화와 URL segment 인코딩을 통일해야 한다. slash, 경로 이동, 제어문자 차단은 유지한다. 과거 URL을 정리할 때는 삭제가 아니라 새 canonical URL로 redirect한다.

### 1.4 긴 글과 캐시 갱신에도 정합성 문제가 있다

| 문제 | 실제 경로 | 필요한 변경 |
|---|---|---|
| 제목·설명·본문 순차 생성 | 앞선 호출이 끝나야 다음 호출 시작 | 짧은 메타데이터는 한 요청으로 묶고 본문과 제한된 병렬 처리 |
| 긴 본문 절단 | 30,000자 이후를 잘라 모델에 전달 | Markdown 블록 단위로 나누고 전체 블록 완료 검증 |
| 생성 직후 검증 누락 | 짧고 불완전한 응답도 캐시에 INSERT | 검증을 통과한 결과만 공개 캐시로 승격 |
| 과도하게 단순한 캐시 버전 | 본문만 32비트 rolling hash로 비교 | 본문·제목·설명·언어·프롬프트·모델/스키마 버전을 실제 SHA-256 등으로 해시 |
| 갱신 누락 | 제목/설명만 바뀌면 이전 캐시 유지 가능 | 영향을 받은 산출물만 정확히 갱신 |
| 삭제 후 재생성 연결 누락 | 캐시 삭제와 처리 완료 outbox 재사용이 별개 | 삭제/무효화가 새 revision 생성 또는 명시적 재실행으로 이어지도록 처리 |

50,000자 원문과 100자 모의 번역을 원본 함수에 넣었을 때 본문 입력은 30,000자와 절단 표시로 바뀌고, 자체 검사로 의심스러운 결과임에도 DB 쓰기가 1회 발생했다. 실제 모델 품질을 평가한 시험이 아니라 **잘못된 결과를 걸러내지 않는 저장 경로의 재현**이다. [E05, 진단 T02]

`sourceContentHash`에 붙인 `sha256:` 접두사와 실제 32비트 해시도 일치하지 않는다. 이름만 바꾸지 말고 버전 계약을 마이그레이션해야 한다. 오래된 작업이 뒤늦게 끝났을 때 현재 원문 버전에 덮어쓰지 못하도록 최종 저장에서 버전을 다시 확인한다. [E03, E05–E06]

### 1.5 권장 번역 UX

처음부터 빈 본문이나 큰 진행 안내로 바꾸지 않는다. 원문을 유지하고 언어 버튼 옆에 `번역 준비 중` 정도만 표시한다. 작업 ID와 실제 상태를 받아 queued/running/ready/failed/deferred를 구분한다. 화면 관찰 기한이 끝났다는 이유만으로 서버 작업을 실패 처리하지 않는다.

긴 글은 검증된 문단 단위로 표시하거나 전체 완료 후 교체하되 읽고 있던 위치를 보존한다. 자동으로 언어가 뒤집혀 읽기를 방해하는 경우에는 `번역 준비됨` 버튼으로 사용자가 전환하게 한다. 재시도는 진행 중인 동일 작업을 다시 연결하고, 명시적인 다시 생성만 새 작업이 된다. 전체 재생성 권한을 얻기 위해 기존 내부 인증을 제거해서는 안 된다.

## 2. AI 응답 지연과 UX

### 2.1 기능마다 응답 방식이 다르다

| 기능 | 현재 확인된 방식 | 해석 |
|---|---|---|
| 핵심 파악·다각도·질문 카드 | `sketch/prism/chain`은 전체 응답을 `res.text()`로 수신한 뒤 파싱 | 완성 전에는 유용한 내용이 보이지 않음 |
| 일반 AI 대화 | 실제 upstream 스트리밍과 SSE 전달, 15초 heartbeat 존재 | “스트리밍이 전혀 없다”는 진단은 잘못됨 |
| 대화 문맥 준비 | notebook/RAG 병렬 처리, 각각 기본 1.8초/2.2초 soft timeout | 이미 있는 병렬화를 중복 구현하지 않고 취소·측정 개선 |
| 스트리밍 실패 후 복구 | 첫 텍스트 전 실패하면 비스트리밍 호출을 다시 수행 | 장애 경로에서는 사용자가 두 번 기다릴 수 있음 |
| 별도 `/ai/generate/stream` | 전체 생성 후 작은 조각으로 나눠 전달 | 이름은 stream이지만 첫 유용한 텍스트가 빨라지지 않음 |
| Redis async 경로 | 큐에 넣고 HTTP 요청 안에서 결과를 기다리는 구현 존재 | 서버 큐 사용과 사용자에게 비동기 작업을 제공하는 것은 다름 |

`/ai/generate/stream`은 검토한 프론트엔드에서 직접 호출하는 참조를 찾지 못했으므로 현재 카드 지연의 원인이라고 단정하지 않는다. 다만 앞으로 재사용하면 잘못된 “실시간” 경험이 반복되는 잠재 문제다. 정상 대화 스트리밍에는 인위적인 조각 지연이 없고 비스트리밍 fallback 쪽에만 존재한다. [E07–E08]

SDK 기본 제한은 120초, 재시도 기본값은 2회다. 이는 실제 응답이 항상 120초 걸린다는 뜻이 아니다. 다른 계층의 재시도와 합쳐질 때 전체 예산이 늘어날 수 있으므로 하나의 전체 deadline 안에서 남은 시간을 전달해야 한다. 실제 공급자 추론 시간·모델 큐 대기·네트워크 비용은 이번 자료로 측정하지 못했다.

### 2.2 최적화 전에 구간을 나누어 측정한다

동일 trace/request ID로 클릭→인증/세션→작업 대기→문맥 확보→공급자 요청→첫 의미 있는 텍스트→완료→화면 표시 시간을 연결한다. 이미 있는 trace header를 확장하고 로그에 본문·비밀키를 저장하지 않는다.

첫 연결 이벤트, heartbeat, 첫 유용한 답변은 별도로 센다. 화면이 즉시 spinner를 띄우는 것과 실제 답이 빨라지는 것은 다르다. p50/p95를 기능·모델·캐시·fallback별로 나누면 무엇을 줄여야 하는지 확인할 수 있다.

초안 목표는 클릭 피드백 100ms 내외, 준비된 캐시 표시 p95 1초 이내다. **현재 측정값이나 달성 보장이 아니라 설계 목표**다. 생성 TTFT 목표는 실제 공급자·모델·문맥 길이를 측정한 뒤 정한다.

### 2.3 권장 화면 동작

카드를 누르면 현재처럼 필요 없는 상단을 줄이고 선택한 기능과 취소 버튼만 남긴다. 기능 소개를 다시 길게 보여주지 않는다. `sketch`는 문장, `prism`은 완성된 관점 하나, `chain`은 검증된 질문 하나씩 표시하는 식으로 결과 자체가 진행을 드러내게 한다. 반쯤 들어온 JSON을 사용자에게 출력하지 않는다.

UI에는 실제 이벤트에 근거한 `문맥 확인 중`, `응답 시작됨`, `다시 연결 중` 같은 짧은 표시만 둔다. 근거 없는 진행률은 표시하지 않는다. 사용자가 위로 스크롤하면 자동 스크롤을 멈추고, 새 내용이 있다는 표시만 남긴다. 접거나 다른 페이지로 이동해도 작업/완료 결과를 버리지 않는 구조가 필요하다.

취소는 의미를 구분한다. 화면만 닫는 것은 관찰을 중단하는 것이며, 생성 취소는 큐 취소 또는 provider AbortSignal까지 전달해야 한다. 공유 번역처럼 여러 사용자가 같은 작업을 보고 있다면 한 사람의 닫기로 전체 작업을 취소하지 않는다. 이미 일부 답변을 받았다면 재시도가 앞부분을 중복 추가하지 않도록 요청 ID와 마지막 수신 위치를 보존한다.

일반 대화·명시적 번역이 이미지/SEO 선생성 뒤에서 기다리지 않도록 요청 종류별 처리 순서와 동시 실행 상한을 분리한다. 무조건 동시성을 높이는 대신 현재 모델의 처리 한도와 사용자 응답 p95를 기준으로 배경 작업을 줄인다.

## 3. AI-server 이미지 생성 도입과 활용

### 3.1 새 기능을 만드는 것이 아니라 기존 구현을 완성하는 작업이다

현재 소스에는 관리자 `AiImageGeneratorPanel`, PostEditorWorkspace 통합, `/api/v1/admin/ai-images/generate`, 이미지 프록시의 `/images/generations` 호출, PNG 검증·저장, WebP 변형, Worker를 통한 원격 이미지 저장, 에이전트 `image_generation` 도구가 있다. 에이전트는 cover/inline/variants 및 cover 후보 반환을 지원한다. 관리자 권한 검사와 서버 idempotency도 존재한다. [E09–E11]

따라서 별도 이미지 API/저장소/갤러리를 중복 개발하지 않는다. 블로그 백엔드가 AI-server를 호출하는 기존 경계를 유지하고, AI-server가 맡는 모델 라우팅·생성과 블로그가 맡는 원문 연결·검증·승인·게시를 분리한다.

### 3.2 운영 연결에서 확인할 항목

| 확인 항목 | 현재 소스와 차이 |
|---|---|
| 기능 활성화 | `FEATURE_ADMIN_AI_IMAGE_ENABLED` 기본 false. 배포에서 실제 활성 상태 확인 |
| 프록시 endpoint와 인증 | `AI_IMAGE_PROXY_BASE_URL/API_KEY`가 AI-server의 이미지 경로를 가리키는지 확인. 키는 브라우저에 전달하지 않음 |
| 실제 모델 기능 | 현재 health는 `/model-names` 탐색. 목록 조회 성공과 이미지 생성 성공은 별개 |
| API 계약 | size/quality/n, base64 또는 URL 반환, 오류 포맷, 요청 ID, timeout을 실제 AI-server 버전과 계약 테스트 |
| 생성 증거 신선도 | 마지막 성공·마지막 확인·실제 불가·증거 만료를 서로 다른 상태로 기록 |
| 저장 경로 | 운영 환경에서 Worker 업로드 및 CDN 읽기까지 확인해야 완성 |

이번에 검토한 것은 **블로그 쪽 어댑터**다. AI-server 최신 스냅샷 자체와 운영 API는 확인하지 못했다. 특정 모델 별칭이나 `/model-names`가 현행 서버에서 유효하다고 가정해서는 안 된다.

### 3.3 더 긴 요청을 기다리게 하기보다 지속 가능한 작업으로 전환한다

현재 관리 API는 생성과 저장을 모두 기다린 뒤 응답하며 기본 이미지 timeout은 300초다. 장시간 HTTP 연결을 유지하는 대신 빠르게 작업 ID를 반환하고, 생성·다운로드·검증·업로드·완료를 서버 작업 기록에 남긴다. 화면은 작업 기록을 조회/구독한다. [E09]

클라이언트의 `Idempotency-Key`는 호출할 때마다 새로 만들어진다. 네트워크가 끊긴 뒤 같은 의도를 재시도해도 새 키가 되어 중복 생성 위험이 있다. 한 번의 생성 의도에 대해 키를 보존하고, 사용자가 “다른 이미지 생성”을 선택했을 때만 바꾼다. 공급자 결과가 만들어졌는데 업로드만 실패했다면 이미지 생성부터 다시 하지 않고 저장부터 재개한다. [E10]

```text
후보 요청 → 기존 image service → AI-server
                             ↓
                    원본 수신·안전성 검사
                             ↓
                   저장·필요한 크기 변환
                             ↓
                   미리보기·검증·승인
                             ↓
                 현재 원문 버전 확인 후 연결
```

기존 대표 이미지는 후보가 준비됐다고 자동 덮어쓰지 않는다. 수동 지정 이미지는 잠그고, 승인한 새 버전만 연결한다. 실패·취소·오래된 원문 기준의 늦은 결과는 현재 게시물의 이미지를 바꾸지 않는다. 생성 모델/요청 ID/입력 버전/프롬프트 버전/출처를 보관한다. 지원되지 않는 seed 등은 임의로 만들어 기록하지 않는다.

### 3.4 블로그에 맞는 활용

| 활용 | 권장 방식 |
|---|---|
| 대표 이미지 | 현재 이미지 미지정 글 중 중요하거나 이미지가 실제 이해에 도움이 되는 글부터 |
| 본문 설명 이미지 | 혼동하기 쉬운 개념 비교·예시를 보조. 기술 관계·수치가 중요한 도식은 검증된 데이터로 SVG/다이어그램 렌더러 사용 |
| 시리즈 이미지 | 공통 visual brief를 재사용하되 각 글의 주제를 구분 |
| Projects | 실제 구현 화면·로그·아키텍처 증거를 우선. AI 일러스트를 실제 제품 screenshot처럼 표시하지 않음 |
| 공유용 이미지 | master 하나로 필요한 비율/포맷을 변환. 모든 크기를 새 AI 호출로 생성하지 않음 |
| 독자 요청 “도식으로 보기” | 별도 quota·공유 캐시·비용 상한 후 도입. 방문만으로 무제한 생성하지 않음 |

기본 블로그는 본문 중심으로 유지한다. 생성 이미지 관리가 필요하면 관리자 자산 화면에서 그리드/목록·사용 중/후보/실패·연결된 글 필터를 제공하고, 읽기 페이지 상단을 대형 생성 패널로 바꾸지 않는다.

## 4. Projects와 About

### 4.1 Projects는 내용 작성 전에 전달 경로를 복구해야 한다

첨부 `project-catalog.json`에는 공개 저장소 68개(원본 59, fork 9, 빈 저장소 2)가 있다. 빈 저장소는 별도의 겹치는 속성이므로 59+9+2로 합산하지 않는다. 반면 화면이 사용하는 `projects-manifest.json`은 total 0 / items []다. 최근 Push나 GitHub public 상태는 운영 완료를 의미하지 않는다. [E12]

Markdown을 스캔하는 generator는 디렉터리가 없어도 만들어 준 뒤 빈 manifest를 정상 저장한다. 기존 검토된 GitHub 증거→프로젝트 Markdown 재생성 스크립트와 `--check`도 있지만 기본 prebuild에는 이 검증 연결이 없다. 아카이브의 Markdown 부재가 실제 repository의 부재인지 export 제외인지 구분하고, 완전한 원본을 확보한 뒤 재생성해야 한다. [E13]

또한 `ProjectService`는 manifest HTTP 오류를 null로 바꾸고 그것을 빈 성공 cache로 저장한다. 첫 응답을 503, 두 번째를 정상으로 둔 재현에서 재시도 호출도 []를 반환했고, clearCache 이후에야 정상 항목을 가져왔다. 네트워크 실패와 실제 항목 0개를 구분하고, 실패 때 마지막 정상 목록을 유지하거나 오류 상태를 보여줘야 한다. [E14, 진단 P01]

### 4.2 전부 나열하는 목록과 실력을 보여주는 사례를 분리한다

전체 공개 저장소 목록은 보존하고, 위에는 대표 사례 4~6개만 둔다. fork/빈 저장소를 원작·완료 제품으로 포장하지 않고 필터에서 구분한다. 한 카드에 상세 설명을 모두 넣기보다 `/projects/:slug` 사례 페이지를 추가한다.

상세 페이지에는 문제, 직접 맡은 부분, 구현 선택 이유, 실패와 복구, 측정 범위가 명시된 결과, 관련 글, 코드/데모, 마지막 검증일을 넣는다. GitHub 공개 여부, 코드 구현 여부, 실제 서비스 확인 상태를 따로 표시한다.

| 후보 | 넣을 가치가 있는 내용 | 공개 전 확인 |
|---|---|---|
| 현재 블로그 | Workers/백엔드 경계, AI 읽기 도구, 번역·이미지·SEO의 실행과 게시 관리 | 실제 완료 기능과 이번 발견 문제 구분 |
| AI-server / Smart Router | 모델 연결, 라우팅, 사용량 제어, 이미지 생성·실패 처리 | 최신 소스·운영 증거 및 공개 가능한 범위 |
| WLatch | 브라우저/브리지 세션 연동, 중복 요청 방지, 복구 설계 | 구현·운영 검증 범위와 비공개 정보 제거 |
| 메타인지 파일 앱 | 파일을 단순 보관하지 않고 이해·판단에 연결하는 제품 흐름 | 계획과 실제 구현을 분리 |
| 기존 공개 catalogue의 ComposeAI·NewsInsight·MAGI-Agent 등 | 기존 검토 요약에서 출발하는 공개 사례 | 해당 저장소별 실제 기능·본인 기여·운영 여부 |

최근 작업에서 의미 있는 결과를 후보로 모으는 자동화는 유용하지만, PR merge를 자동으로 운영 성과로 바꿔 쓰면 안 된다. 공개 가능한 근거를 검증한 뒤 사람이 선택한 대표 사례만 About에 연결하는 방식이 적합하다.

### 4.3 About은 기술명 나열보다 무엇을 만들고 확인했는지를 보여준다

현재 About에는 `2026년 졸업 예정`, 연도별 개괄 이력, 많은 기술 배지와 설명이 하드코딩돼 있다. 2026-09-10이라는 이유만으로 졸업했다고 바꿀 수는 없다. 실제 이력과 마지막 확인일을 갱신 대상으로 두고, 근거가 없는 부분은 그대로 두거나 간단히 줄인다. [E15]

권장 순서는 짧은 소개, 대표 작업 3개, 일하는 방식, 확인된 기술 경험, 연락이다. “Kubernetes 기초”를 근거 없이 “전문가”로 높이지 않고, 실제로 수행한 배포·장애 복구 사례가 있다면 그 사례에 연결한다. 한국어/영어 전환도 본문 언어와 함께 맞춘다.

소개 초안은 예를 들어 “AI 도구를 만들고, 실제 사용 중 드러난 문제를 고칩니다. 모델 연결과 작업 실행, 실패 복구, 화면에서 결과를 읽는 경험을 함께 다룹니다.”처럼 작업 중심으로 쓸 수 있다. 이것은 게시 제안이며 확인되지 않은 경력 사실을 추가하는 것이 아니다.

자동 갱신은 프로젝트 후보·사실 변경 후보까지 맡기고 학력·경력·역할·성과 수치는 확인 없이 공개하지 않는다. 연락 폼은 이미 중복 제출 방지와 실패 시 입력 보존이 있으므로 유지한다.

## 5. SEO 자동화 설계

### 5.1 생성량보다 먼저 크롤링·canonical·본문 응답을 고친다

| 문제 | 확인 결과 | 변경 |
|---|---|---|
| 검색봇의 자산 요청에 HTML | Googlebot의 robots/sitemap/png/js 요청 모두 index HTML 200으로 재현 | 모든 UA에 대해 자산/제어 파일 먼저 분기 |
| `/projects` 대표 URL 오류 | resolver가 Projects를 처리하지 않아 홈 URL 사용 | 실제 공개 route 목록과 SEO resolver를 동기화 |
| 한글/공백 slug | URL 인코딩된 slug를 그대로 비교해 실제 글을 못 찾음 | 안전한 decode/normalize/lookup 공통화 |
| 존재하지 않는 글의 200 | 모의 미존재 post 요청도 shell 200 | 실제 없는 글 404; 일시적 장애는 별도 5xx로 구분 |
| static HTML에 본문 없음 | generator는 메타 태그만 바꾸고 빈 React root 유지 | 전체 공개 본문을 포함한 SSG/prerender |
| 생성한 페이지 HTML 우회 | 일반 사용자 extensionless 요청도 index.html로 반환 | 실제 route 산출물을 먼저 제공 |
| article:tag 반복 누적 | useSEO가 매번 append, 정리 없음 | page/version 단위로 소유 태그를 정확히 교체 |
| 수정일 부정확 | 글 dateModified=작성일, 일반 페이지 lastmod=빌드 시각 | 실제 의미 있는 내용 변경시각 사용 |

E16~E20 및 진단 S01~S03에서 확인했다. production wrangler에는 도메인 전체 경로가 연결되므로 현재 동일 버전이 배포돼 있다면 영향 범위가 넓다. 배포 버전과 실제 Googlebot 요청 로그로 최종 확인해야 한다.

JavaScript 사이트가 무조건 색인되지 않는 것은 아니다. Google은 JavaScript를 렌더링할 수 있다. 그러나 중요한 자산이 HTML로 돌아오거나 초기 HTML에 본문이 없는 상태는 별개의 전달·의존성 문제이므로, 사용자와 검색봇 모두 동일한 완성 콘텐츠를 받도록 고치는 것이 이 프로젝트에는 타당하다. [G3]

canonical은 대표 URL을 전달하는 신호다. Projects에 홈 주소가 전달되는 오류와 기존 canonical 중복 가능성을 제거하고, API/프론트/빌드의 SEO 규칙을 하나의 page artifact 데이터에서 생성하도록 통합한다. [G7]

### 5.2 자동화의 단위는 “작업 횟수”가 아니라 “변경된 공개 콘텐츠 버전”이다

```text
발행·의미 있는 수정·확정된 프로젝트 갱신
  → 공개 범위/버전 확인
  → 기존 정상 산출물과 비교
  → 빠진 것·무효화된 것만 작업 등록
  → 정적 메타데이터 생성 / 필요한 이미지 후보 생성
  → 콘텐츠·구조·이미지·URL 검증
  → 수동 잠금 및 승인 정책 확인
  → 현재 버전일 때만 manifest/본문/SEO를 함께 공개
  → sitemap·캐시 갱신
  → Search Console/페이지 성능 측정으로 다음 개선 후보 선정
```

원문 제목·설명·본문·언어·의미 있는 이미지 입력, 정책/프롬프트/스키마 버전을 포함하는 해시를 사용한다. 같은 입력에 같은 작업이 중복 등록되면 하나로 합친다. 다만 이미 처리된 작업의 결과물이 삭제된 경우에는 복구 revision을 만들어 정상적으로 다시 처리한다. 정책 버전이 바뀌었다고 모든 글 이미지를 한꺼번에 교체하지 않는다.

단계별 저장을 두어 생성은 성공하고 업로드만 실패했을 때 재생성 비용을 피한다. 작업이 완료되는 순간 현재 게시물 버전과 비교하여 오래된 결과면 후보 보관함으로 보내고 현재 글을 덮어쓰지 않는다. 검증/게시 실패 시 마지막 정상 본문·이미지·canonical은 계속 제공한다.

### 5.3 무엇을 자동화하고 무엇을 잠글 것인가

| 자동화해도 좋은 항목 | 정책/확인이 필요한 항목 |
|---|---|
| canonical 일관성·깨진 링크·content-type·404 검사 | 글 제목을 클릭 유도형으로 바꾸는 편집 |
| 실제 metadata 기반 BlogPosting·author·날짜 생성 | 경력·성과·벤치마크 사실 추가 |
| 이미지 크기/포맷 변환과 URL 확인 | 기존 수동 대표 이미지 교체 |
| 공개 URL sitemap 및 실제 수정일 | 새 번역본 공개·색인 허용 |
| 미지정 설명/alt/대표 이미지 후보 | AI가 판단한 내부 링크·인용의 공개 반영 |
| 검색 성과/오류에서 점검 후보 생성 | 원문과 다른 의미의 문구·도식 게시 |

AI가 제목·설명·alt를 제안할 수는 있지만 게시물에 없는 내용을 만들면 안 된다. Google도 생성형 AI 자체보다 정확성·관련성·사용자 가치를 강조하며, 가치 없는 페이지 대량 생성은 scaled content abuse에 해당할 수 있다고 안내한다. 순위를 보장하는 엔진이 아니라, 오류와 실제 빈칸을 찾아 제한된 자원으로 보완하는 작업기로 설계한다. [G1]

### 5.4 이미지 자동화는 master 하나와 파생 파일로 구성한다

88개 이미지 미지정 글을 모두 생성 대상으로 바로 확정하지 않는다. 텍스트 전용으로 잠근 글, 변경 없는 글, 비공개 글은 건너뛴다. 중요한 글, 주제를 이해하는 데 이미지가 필요한 글, 검색 노출은 있으나 표현 개선이 필요한 글부터 검토한다. Search Console 접근과 데이터는 앞으로 연결할 대상이며 이번 분석에서 실제 노출/CTR을 읽은 것은 아니다.

승인 가능한 master 1장을 만든 뒤 저장 서비스로 카드·본문·대표 이미지 크기와 WebP/필요 시 AVIF를 파생한다. 콘텐츠 해시 기반 안정적인 URL, 실제 폭/높이, `srcset`과 기본 `src`, 본문 관련 위치, 실제 그림을 설명하는 alt를 기록한다. 장식 이미지는 적절히 빈 alt를 사용할 수 있고 키워드를 반복해서 넣지 않는다. Google은 `<img src>`로 이미지를 발견하며 CSS background는 색인하지 않는다고 안내한다. [G2]

2026-03-02 갱신된 Google 이미지 문서는 preferred image에 페이지를 대표하는 관련 이미지·고해상도·과하지 않은 비율을 권하고, 일반 로고나 글자가 들어간 이미지는 피하라고 안내한다. 따라서 제목 글자가 대부분인 자동 OG 카드만 계속 찍는 전략보다 글별 대표 이미지를 만드는 편이 더 맞다. 별도 홍보 카드가 필요하면 대표 검색 이미지와 관리 목적을 구분한다. 기존 agent 프롬프트의 no visible text/no logos 원칙도 유지할 가치가 있다. [G2, E11]

### 5.5 번역 SEO와 저자 정보까지 연결한다

언어 버튼만 바꾸는 것과 각 언어 페이지를 독립적으로 노출하는 것은 다르다. 검증된 번역에만 `/en/blog/...` 같은 고유 URL을 발급하고 각 언어의 self-canonical 및 상호 hreflang을 생성한다. 번역이 준비되기 전에는 실체 없는 언어 URL을 sitemap에 추가하지 않는다. 원문과 번역을 서로 다른 글처럼 복제 증식시키지 않고 같은 콘텐츠의 언어 버전으로 관리한다. [G4]

BlogPosting에는 실제 제목, 작성/수정일, 대표 이미지, 저자 이름과 About URL을 연결한다. 직접 작성/검토한 범위와 AI가 보조한 범위도 독자가 확인할 수 있게 한다. 구조화 데이터는 페이지 내용을 설명하는 것이며, 없는 평가·성과·저자 정보를 만들어 넣어서는 안 된다. Google Article 가이드는 author URL을 통한 저자 식별도 권장한다. [G5]

sitemap에는 실제 공개 canonical URL만 넣고 의미 있는 변경을 `lastmod`에 반영한다. 빌드할 때마다 과거 글을 새 글처럼 보이게 하지 않는다. sitemap 제출은 크롤링·색인 보장이 아니라 발견을 돕는 신호라는 점도 운영 지표에 반영한다. [G6]

### 5.6 상시 운용의 안전장치

같은 outbox 관측·재시도·중복 방지 기반을 재사용하되 사용자 대화와 저우선순위 SEO 작업을 분리한다. 일별/월별 생성 비용, 이미지 수, 토큰, 저장공간, 재시도 횟수에 상한을 둔다. 가격은 현재 AI-server 모델 계약에서 읽고 실제 usage와 정산한다. 실패도 과금될 수 있는 경계를 고려한다.

전경 요청 대기시간 악화, 지정 공급자 실패, 예산 소진 때 배경 작업은 멈추고 그 이유를 관리자에게만 표시한다. 공개 화면에는 SEO 운영 설명을 상시 노출하지 않는다. 작업 장부는 원문 버전, 산출물 버전, 검증/승인자 또는 정책, 비용, 오류, 다음 재시도, 취소/복구 기록을 남긴다. 허용하지 않은 비공개 문서·키·개인 대화를 프롬프트에 넣지 않는다.

## 실행 순서와 완료 판단

`tasks.md`에 제안 PR-A01~A10을 분리했다. 실제 PR 생성이나 구현 완료를 의미하지 않는다.

첫 단계에서 SEO 게이트웨이 자산·route 응답, 번역 실행/상태, Projects 목록을 복구한다. 그다음 번역 품질·버전, 실제 스트리밍·취소, 이미지 작업 저장을 보강한다. 이후 전체 HTML/언어 SEO, 증거 기반 Projects/About, 비용 제한된 자동 SEO를 연결한다.

완료 기준은 “버튼이 생겼다”가 아니다. 사용자가 원문을 읽는 동안 작업이 실행되고, 결과가 검증된 뒤 현재 콘텐츠에 반영되며, 재시도/실패/동시에 바뀐 원문 때문에 기존 정상 글이 손상되지 않아야 한다. 검색봇과 일반 방문자에게 같은 공개 콘텐츠와 올바른 자산을 전달하는 것도 함께 확인해야 한다.
